# Architecture notes

- **Single file:** `index.html` holds markup, CSS and JS. No build step; open it or host it as-is (GitHub Pages).
- **Engine:** deterministic game logic. Online play shares only *inputs* (dice rolls, market purchases + targets, power-ups) as a compact move log; every browser replays it, so all boards match.
- **Move log grammar:** a unit is one of: a roll `1-6`; a special-die roll `[slg][1-8]` (steady / lucky / gambler); no-target actions `b t c H C` plus the RPG items `r i p k n z e v`; targeted actions `[wfmSFoda][JKLMN]` (J..N = player 1..5); a Jack of Trader purchase `x0`-`x2` and its host-drawn outcome `y[a-t][0-9]`; decisions `A D` (altar) and `u q` (alliance accept / decline).
  Market codes: swap `w`, bribe `b`, freeze `f`, checkpoint `c`, serpent `t`, mine `m`, Jack `x`, rewind `r`, mirror `i`, loaded dice `z`, cloak `p`, hook `k`, bounty `o`+target, lightning `n`. Arena: duel `d`+target, offer `a`+target, competition `e`, betray `v`. Power-ups: swap `S`, freeze `F`, shield `H`, cash `C`.
- **RPG layer (shared randomness):** the room record also carries `mode` (a record without one plays as `classic`) and a host-made `seed`. Every shared RPG outcome (board layout, chests, wheel, portals, world events, boss and duel dice, traps) is drawn from a mulberry32 PRNG seeded from it and advanced only by replayed log units, so all clients get identical results. Only the roller's own die still comes from `Math.random` and is logged. Decisions made by a seat other than the acting one use `NET.decWait`; the answer comes back through the log. Details in `RPG-DESIGN.md`.
- **Online transport:** `MQTTRoom` in `index.html` publishes each player's presence (name, class, game record) as a retained message on `dungeon-sl-v1/<room>/<id>` with a last-will to clear it. Brokers are tried in order (EMQX, HiveMQ, Mosquitto).
- **Rooms:** host's record (generation 0) is the lobby; "Start match" creates generation 1. Higher generation wins; seats are tied to a per-tab session token so reloads rejoin.
- **Tests:** `tests/online-sync.test.js` runs 2- and 5-player games in jsdom against a fake MQTT broker and checks all clients end in identical state, plus reload-rejoin and broker failover. `tests/menu-chat.test.js` covers the menu flows, the invite link, and chat (delivery, no echo duplicates, forged/malformed messages, mute, rate limiting, XSS safety, keyboard guard, no replay on rejoin).
- **Main menu:** `#main-menu` is a full-screen overlay (z-index below the dialogs) with a game-mode pane (Snake Game / Party Game placeholder), a home pane and a solo pane. Play Solo → opponent → the existing champion screen; Play Online → the online dialog; How to Play → `#help-modal`. Each dialog remembers whether it was opened from the menu (`classFromMenu`, `onlineFromMenu`) so Back returns there. `matchActive` drives the Resume button. The menu counts as a modal in `anyModalOpen()`, so rolls and shortcuts are blocked behind it. An invite link (`#room-XXXX`) skips the menu and opens the Join tab.
- **Chat ("Table Talk"):** separate from the replicated game state. `MQTTRoom` subscribes to a second, non-retained topic `dungeon-sl-v1-chat/<room>` (outside the presence namespace) and exposes `chat(obj)` / `onChat(fn)`. Messages are `{t: token, k: 'q'|'e'|'m', i: index | s: text}`; quick chat and emoji send only an index into fixed lists. Receivers accept a message only from a seated token, validate the index/kind, clean and cap typed text (80 chars), rate-limit per sender, ignore their own echo, and render with `textContent`. The drawer, unread badge and token bubbles live in `chat*` functions in `index.html`.
- **Key handling:** the global key handler ignores events from `INPUT`/`TEXTAREA`/`SELECT`, so typing in chat, the name box or the room code never rolls the dice (Space) or opens the Black Market (S).
- **Welcome splash and music:** `#intro` is a full-screen overlay (z-index 90) shown from the first paint. `introStart()` (tap, button, or any key) calls `Tone.start()` inside the gesture, then fades the splash out and removes it. While it is up the global key handler swallows every key so nothing reaches the game underneath. The music (`buildMusic()`) is generated live: a pad, arpeggio, lead melody, bass, drum and shaker as looping `Tone.Part`s on the shared Transport, routed through one `Tone.Volume` bus. It uses the convolver-based `Tone.Reverb` rather than Freeverb so it needs no AudioWorklet. `musicSync()` sets the bus level (louder on splash/menus, quieter during a match), mutes it when Audio or Music is off or the tab is hidden, and pauses the Transport. Audio is the master switch; Music (`sl-music` in localStorage) is separate.

## party.html (Save the Princess)
Standalone single file; online play uses only public MQTT brokers (no backend). One 960×540 canvas plus a DOM overlay for menus. Mini-games register through `reg({id, cat, min, max, make(G)})`; `make` returns `{think, update, draw, done, score}`. Every seat is reduced to five buttons (left/right/up/down/action) so keyboards, touch and bots share one input array — bots just write into it in `think()`. All-bot rounds are simulated instantly with the same code. The adventure (map graph `NODES`, routes, cards, shop, events, boss and castle stages) is a promise-driven loop in `playMatch()`.
Controls (in `party.html`): a pointer-event floating joystick (8-way sector mapping with hysteresis) and context buttons feed the same five-button `INP` array through `tsApply`. Each game declares `goal` and `ui` (`mv`: `joy|lr|dpad|none`, `act`, `ai`, `alt`) in the `UIX` table; a game may also return `actLabel(i)` so the action button relabels itself live (e.g. CHARGE → RELEASE). Every mini-game must support 2–4 players (`pickGame` filters on `min <= n <= max`).
Audio: `TRACKS` defines five generated songs (chords, bass, arpeggio, drums, melody); `musPlay(name)` rebuilds the `Tone.Part`s and restarts the Transport on a track change, and `TRACK_OF` maps each mini-game category to a track.
Online (`party.html`, section "online"): host-driven lockstep over MQTT (mqtt.js from jsDelivr; brokers tried in order `wss://broker.emqx.io:8084/mqtt`, `wss://broker.hivemq.com:8884/mqtt`, `wss://test.mosquitto.org:8081`). Topics `sl-party-v1/<room>/h` (host → all) and `/c` (clients → host). Control messages are QoS 1 with a sequence number; per-frame input records (`[seat0..3]`, each = 6-bit hold mask | edge bits << 6) and heartbeats are QoS 0 with resend-on-gap (`need`). A round is made deterministic by seeding `Math.random` for *logic only* (`withRng(R, fn)`; drawing keeps real randomness) and stepping a fixed 1/60 s; the host ends the round and its scores are authoritative (`re` carries the frame count and a score hash — mismatches are counted in `NET.dbg.desync`). Adventure state is mirrored with `snapM()/applySnap()` and DOM overlays are mirrored as sanitised HTML (`ov`, `bn`, `sp`, `wp`, `lobby`…). `ask(html, w, {who, all, def})` routes a prompt to the seat that owns the decision while others see it read-only. Players who drop become bots after the round (`netLost`). Rule for new mini-games: all gameplay randomness must go through `Math.random`/`G.rand` inside `think/update` (never `performance.now()` or wall-clock) so lockstep stays in sync.
