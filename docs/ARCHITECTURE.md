# Architecture notes

- **Single file:** `index.html` holds markup, CSS and JS. No build step; open it or host it as-is (GitHub Pages).
- **Engine:** deterministic game logic. Online play shares only *inputs* (dice rolls, market purchases + targets, power-ups) as a compact move log; every browser replays it, so all boards match.
- **Move log grammar:** rolls `1-6`; no-target actions `b t c H C`; targeted actions `[wfmSF][JKLMN]` (J..N = player 1..5).
  Market codes: swap `w`, bribe `b`, freeze `f`, checkpoint `c`, serpent `t`, mine `m`. Power-ups: swap `S`, freeze `F`, shield `H`, cash `C`.
- **Online transport:** `MQTTRoom` in `index.html` publishes each player's presence (name, class, game record) as a retained message on `dungeon-sl-v1/<room>/<id>` with a last-will to clear it. Brokers are tried in order (EMQX, HiveMQ, Mosquitto).
- **Rooms:** host's record (generation 0) is the lobby; "Start match" creates generation 1. Higher generation wins; seats are tied to a per-tab session token so reloads rejoin.
- **Tests:** `tests/online-sync.test.js` runs 2- and 5-player games in jsdom against a fake MQTT broker and checks all clients end in identical state, plus reload-rejoin and broker failover. `tests/menu-chat.test.js` covers the menu flows, the invite link, and chat (delivery, no echo duplicates, forged/malformed messages, mute, rate limiting, XSS safety, keyboard guard, no replay on rejoin).
- **Main menu:** `#main-menu` is a full-screen overlay (z-index below the dialogs) with a game-mode pane (Snake Game / Party Game placeholder), a home pane and a solo pane. Play Solo → opponent → the existing champion screen; Play Online → the online dialog; How to Play → `#help-modal`. Each dialog remembers whether it was opened from the menu (`classFromMenu`, `onlineFromMenu`) so Back returns there. `matchActive` drives the Resume button. The menu counts as a modal in `anyModalOpen()`, so rolls and shortcuts are blocked behind it. An invite link (`#room-XXXX`) skips the menu and opens the Join tab.
- **Chat ("Table Talk"):** separate from the replicated game state. `MQTTRoom` subscribes to a second, non-retained topic `dungeon-sl-v1-chat/<room>` (outside the presence namespace) and exposes `chat(obj)` / `onChat(fn)`. Messages are `{t: token, k: 'q'|'e'|'m', i: index | s: text}`; quick chat and emoji send only an index into fixed lists. Receivers accept a message only from a seated token, validate the index/kind, clean and cap typed text (80 chars), rate-limit per sender, ignore their own echo, and render with `textContent`. The drawer, unread badge and token bubbles live in `chat*` functions in `index.html`.
- **Key handling:** the global key handler ignores events from `INPUT`/`TEXTAREA`/`SELECT`, so typing in chat, the name box or the room code never rolls the dice (Space) or opens the Black Market (S).
- **Welcome splash and music:** `#intro` is a full-screen overlay (z-index 90) shown from the first paint. `introStart()` (tap, button, or any key) calls `Tone.start()` inside the gesture, then fades the splash out and removes it. While it is up the global key handler swallows every key so nothing reaches the game underneath. The music (`buildMusic()`) is generated live: a pad, arpeggio, lead melody, bass, drum and shaker as looping `Tone.Part`s on the shared Transport, routed through one `Tone.Volume` bus. It uses the convolver-based `Tone.Reverb` rather than Freeverb so it needs no AudioWorklet. `musicSync()` sets the bus level (louder on splash/menus, quieter during a match), mutes it when Audio or Music is off or the tab is hidden, and pauses the Transport. Audio is the master switch; Music (`sl-music` in localStorage) is separate.
